# Plan9Basic — automated tests

A headless runner that compiles and executes `.bas` programs with no IDE and no
UI, and reports the assertions they collect. It exists to give the engine and
library refactorings a safety net.

## Running

```powershell
.\tests\build.ps1 -Run
```

The script locates `dcc64.exe` through the RAD Studio registry keys, compiles
`Plan9BasicTest.dpr` into `tests\bin\`, and runs the suite in `tests\suite\`.
Exit code: `0` if everything passed, `1` if anything failed.

Running one file or folder:

```powershell
.\tests\build.ps1 -Run -Path .\suite\06_strings.bas
```

## Smoke mode

The programs in `Examples/` and `Demos/` have no assertions — they were written
to be checked by eye. Smoke mode only requires that they compile and run
without a runtime error, which turns them into a regression net:

```powershell
.\tests\build.ps1 -Run -Smoke -Path ..\Examples\01_stdlib_test.bas
```

The runner also scans the output for `[FAIL]` and `[ASSERT FAILED]` lines,
because several examples report their own result by printing. Without that, a
file printing nothing but failures would still pass.

By default only the non-GUI libraries are registered. Examples that create
windows need GUI mode below.

## GUI mode

```powershell
.\tests\build.ps1 -Run -Gui
```

Registers the FMX libraries as well and runs `tests\gui\`. **No window is ever
displayed**: `form#()` builds the form and `form_show#()` is a separate call the
suites never make. That makes almost the whole control property surface
checkable automatically.

Between files the runner repeats the teardown order documented in
`InitBASICEngine`: timers, forms, engine, GC.

The GUI libraries **do not raise** on an invalid handle — they record it in
`xxx_error()`. That makes handle validation checkable from inside the program
itself:

```basic
button_clearerror()
r$ = button_text$(junk#)
ok = 0
if button_error() <> 0 then ok = 1
assert_eq(ok, 1, "an invented address is rejected")
```

| File | Subject |
|---|---|
| `gui/00_smoke.bas` | form and control created, property round trip |
| `gui/01_controls.bas` | one instance of each control type |
| `gui/02_handles.bas` | fabricated pointer, nil, wrong class, freed handle |
| `gui/03_effects.bas` | generated: 64 effects, 200 properties |

`gui/02_handles.bas` is what validates, in the real libraries, the replacement
of `TObject(P) is TBasXxx` by `HandleRegistry`.

`gui/03_effects.bas` is generated by `tests/gen_effects_suite.py` from
descriptors extracted from the effect units themselves. The suite checks those
descriptors against the current code, which validates them before any attempt to
regenerate the units from them. Regenerate with:

```bash
python tests/gen_effects_suite.py
```

## Writing tests

Each file in `suite/` is an ordinary BASIC program using the assertion functions
below. A file with no assertions is reported as `EMPTY`, not as passing.

| Function | Effect |
|---|---|
| `test_case(name$)` | labels the assertions that follow |
| `assert_true(n)` / `assert_true(n, msg$)` | fails if `n` is zero |
| `assert_false(n)` / `assert_false(n, msg$)` | fails if `n` is not zero |
| `assert_eq(a, b)` / `assert_eq(a, b, msg$)` | numeric equality with a relative epsilon |
| `assert_eq(a$, b$)` / `assert_eq(a$, b$, msg$)` | string equality |
| `assert_near(a, b, tol)` / `assert_near(a, b, tol, msg$)` | equality with an explicit tolerance |
| `test_fail(msg$)` | unconditional failure |
| `test_passed()` / `test_failed()` | running counters |

A failure records the case, the line and the value obtained, and execution
**continues** — one run shows every problem, not just the first.

That differs from the language's built-in `ASSERT` statement, which only fires
with `TRACE` on and stops the program at the first failure. `ASSERT` remains the
debugging tool; these functions are for suites.

### Language constraints that shape the tests

A boolean expression is only valid inside an `IF`/`WHILE`/`UNTIL` condition.
You cannot write `assert_true(2 > 1)` or `x = 2 > 1`. The idiom used across the
suite is:

```basic
ok = 0
if 2 > 1 then ok = 1
assert_eq(ok, 1, "2 > 1")
```

Functions returning a number are not valid as a condition on their own either —
they need a comparison: `if dict_haskey(d#, "k") <> 0 then ...`.

## Negative suite

`negative/` holds programs the engine **must** reject. They run with
`--expect-fail`, which inverts the verdict: passing cleanly is a failure.
`build.ps1` runs both suites when no `-Path` is given.

| File | Must be rejected because |
|---|---|
| `01_too_many_globals.bas` | 520 globals, above the ceiling of 513 |
| `02_fabricated_array_handle.bas` | an invented pointer passed to ArrayLib |
| `03_fabricated_dict_handle.bas` | the same for DictLib |
| `04_fabricated_arr_free.bas` | the same for `arr_free` |

For the last three what matters is *how* they fail: the message must be the
library's own diagnostic, not an access violation. Validation now consults
`HandleRegistry` by pointer value instead of dereferencing it — on Android and
Linux that dereference killed the process.

Test working files are written under `bin/`, which is not versioned.
